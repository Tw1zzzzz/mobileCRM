# Бета-сервер Pulse для Android — дизайн

## Зачем

Сейчас Android-приложение хранит всё на телефоне: локальные аккаунты, данные по разделам, никакой аналитики.
Клиент сервера в ядре уже написан (`core/.../api/Api.kt`: `ApiClient`, `RemoteAuthService`, `SyncEngine`),
контракт — `docs/API.md`, но сервера нет, и переключатель `AppConfig.backend` стоит на `Local`.

Нужен **сервер для закрытого бета-теста** Android-версии:

- настоящая регистрация и вход, с подтверждением почты и сбросом пароля;
- все данные игрока хранятся на сервере и возвращаются при входе на другом телефоне;
- команды по-настоящему: стафф создаёт команду, игроки вступают по коду, стафф видит **реальные** данные своих
  игроков (сейчас экраны стаффа работают только на демо-данных, регистрация стаффа без сервера запрещена);
- продуктовая аналитика использования для разработчика: чем пользуются, как часто, сколько времени на какой вкладке,
  какие экраны полезнее, — и закрытый дашборд, где это видно;
- минимальный лендинг, на котором живёт дашборд и обязательные страницы.

Успех: тестировщик ставит бета-сборку, регистрируется с подтверждением почты, пользуется, переустанавливает
приложение или берёт другой телефон — и все его данные на месте. Стафф видит своих игроков. Владелец открывает
`/admin` и видит, как тестировщики пользуются приложением.

## Решения владельца

- **Только Android.** iOS остаётся на локальном хранении, его не трогаем.
- **Хостинг — Vercel** (аккаунт владельца `tw1zzzzz`, сейчас тариф Hobby, проектов Pulse и баз данных нет).
- **Это бета, а не прод.** Пользователи — тестировщики; при регистрации они **обязаны принять условия
  бета-тестирования**. Hobby для беты подходит; переход на Pro ($20/мес) — перед настоящим запуском.
- **Все данные реальные**, регистрация настоящая (с почтой).
- **Аналитика — про использование приложения**, не про деньги: сессии, частота, время на вкладках и экранах,
  какие функции используют, какие экраны полезнее, воронка новичка, удержание по когортам. Подход — по
  Красинскому: смотрим на ценность через удержание и частоту ключевого действия, всё — в разрезе когорт и сегментов.
  Платёжные метрики (UA, C1, ARPPU, APC, CLTV, CAC) **закладываем в схему** (тариф, источник установки), но не
  считаем — платежей пока нет.
- **Дашборд — на своём лендинге**, закрытый раздел `/admin`.
- **Лендинг — по минимуму**, силы — на API и дашборд.
- **Прокси Faceit не нужен:** ключ Faceit (client-side) уже встраивается в сборку через `local.properties` →
  `BuildConfig.FACEIT_API_KEY` (незакоммиченная работа в основной папке; коммитит её сессия, которая её делает).
- **Риск 152-ФЗ принят владельцем для закрытой беты** (данные россиян, включая данные о здоровье, хранятся вне РФ).
  Перед продом базу может понадобиться перенести к российскому провайдеру — см. «Переносимость».

## Что не делаем (non-goals)

- iOS-клиент сервера.
- Прокси Faceit, ежедневные снимки ELO на сервере.
- AI-распознавание еды на сервере (`/food/analyze`) — остаётся ручной ввод / мок.
- Пуши с сервера (FCM). Локальные напоминания на телефоне работают как сейчас.
- Платежи, тарифы, подписки.
- Построчная синхронизация (этап 2 из `docs/API.md`) — храним документ коллекции целиком.
- Полноценный маркетинговый лендинг.
- Перенос локальных аккаунтов, созданных на телефоне до бета-сборки, на сервер.
- Закрытый тест Google Play (раздаём APK напрямую).

## Анти-цели (провал, даже если «работает»)

- Тестировщик потерял данные: переустановил приложение / сменил телефон, а записей нет.
- В аналитику утекли значения здоровья: часы сна, калории, пульс, вес, ответы анкеты. В событиях — только факт
  действия и технические свойства.
- Стафф видит то, что ему видеть нельзя: игроков чужой команды, личные (`personal`) записи дневника, ответы
  анкеты «Игровой характер» по пунктам, данные соло-игроков.
- Демо-аккаунты пишут на сервер или в аналитику и портят цифры.
- Пароли или токены в открытом виде в базе или в логах.
- Приложение «висит» или теряет записи без интернета: офлайн оно работает как сейчас, сервер догоняет позже.

## Архитектура

```
server/            Next.js (App Router, TypeScript) — один проект Vercel «pulse»
  /                лендинг (минимальный)
  /admin           дашборд аналитики (закрыт)
  /privacy /terms /beta-terms /delete-account   обязательные страницы
  /v1/...          API для Android (контракт docs/API.md + дополнения ниже)
androidApp/, core/ клиент: включение сервера, новые экраны почты, синхронизация, аналитика, стафф
```

- Код сервера — **в этом репозитории**, папка `server/`, рядом с `androidApp/` (моё решение: сервер и клиент
  меняются вместе). Vercel-проект берёт `server/` как Root Directory; деплой — через Git-интеграцию с
  `github.com/Tw1zzzzz/mobileCRM` (ветка беты — на усмотрение строителя, по умолчанию `android`).
- **База — Postgres (Neon из маркетплейса Vercel).** Подключает владелец (нужно принять условия Neon в Vercel).
- **Почта — Resend.** Нужен **свой домен** (письма с `vercel.app`/`gmail.com` слать нельзя). Домен покупает
  владелец; DNS-записи для Resend (SPF, DKIM) строитель подсказывает.
- **Ошибки — Sentry** (сервер и Android), бесплатный тариф. Мое решение; если владелец не заведёт аккаунт —
  сервер логирует ошибки в логи Vercel, этого достаточно для беты.
- Секреты (`DATABASE_URL`, ключ подписи токенов, `RESEND_API_KEY`, `ADMIN_EMAILS`, DSN Sentry) — только в
  переменных окружения Vercel. В репозитории — `.env.example` без значений.

### Переносимость (моё решение, из-за 152-ФЗ)

Сервер не должен зависеть от Vercel-специфичных хранилищ: только Postgres по стандартному драйверу, миграции SQL
в репозитории, фото — в той же базе. Тогда перед продом базу можно переехать в Yandex Cloud / Selectel, сменив
`DATABASE_URL`, а сервер — при необходимости поднять там же как обычное Node-приложение.

## API

Базовые правила — как в `docs/API.md`: `https://<домен>/v1`, JSON `snake_case`, ISO 8601 UTC, конверт
`{ success, data, error: { code, message }, meta }`, UUID записей создаются на телефоне, access-токен ~15 минут,
refresh ~30 дней. Ниже — что из контракта делаем и что добавляем.

### Регистрация и вход — с подтверждением почты

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/auth/register` | как в `docs/API.md` + `accepted_beta_terms: true`, `beta_terms_version` | `{ pending_verification: true, email }` — **токенов нет** |
| POST | `/auth/verify-email` | `{ email, code }` | `{ user, access_token, refresh_token }` |
| POST | `/auth/resend-code` | `{ email }` | `{}` |
| POST | `/auth/login` | `{ email, password }` | `{ user, access_token, refresh_token }`; если почта не подтверждена — ошибка `email_not_verified` и новый код уходит на почту |
| POST | `/auth/refresh` | `{ refresh_token }` | `{ access_token, refresh_token }` (ротация: старый refresh гасится) |
| POST | `/auth/logout` | `{ refresh_token }` | `{}` |
| POST | `/auth/password-reset` | `{ email }` | `{}` всегда (не раскрываем, есть ли адрес) |
| POST | `/auth/password-reset/confirm` | `{ email, code, new_password }` | `{ user, access_token, refresh_token }`; все прежние сессии гасятся |

- Код — **6 цифр**, живёт 15 минут, не больше 5 попыток ввода; вводится в приложении (моё решение: на телефоне
  удобнее, чем ссылка).
- Новые коды ошибок: `email_not_verified`, `invalid_code`, `code_expired`, `too_many_attempts`, `rate_limited`.
  Тексты для приложения — на русском, в стиле существующих `AuthError`.
- Роли и команды — как в `docs/API.md`: `teamPlayer` обязан ввести существующий `team_code` (`team_not_found`),
  `staff` вводит `team_name`, сервер создаёт команду и **код приглашения** (короткий, читаемый, уникальный).
- Пароль хранится только хешем (argon2id или bcrypt — на усмотрение строителя). Refresh-токены хранятся хешем.
- Лимиты: `/auth/*` — не больше 10 запросов в минуту с IP и 5 кодов в час на адрес; остальное — 120 в минуту на
  пользователя. Реализация — на усмотрение строителя (таблица в Postgres подойдёт, внешний Redis не обязателен).
- Демо-аккаунты (`player@`/`solo@`/`staff@pulse.app`) на сервере **не регистрируются**: сервер отвечает
  `email_taken` на эти адреса; в приложении они остаются локальными.

### Профиль

| Метод | Путь | Описание |
|---|---|---|
| GET | `/me` | текущий пользователь (+ команда и её код для стаффа) |
| PATCH | `/me` | `{ nickname?, faceit_url? }` |
| DELETE | `/me` | удаление аккаунта и **всех** данных (включая фото и события аналитики, связанные с пользователем) |

Удаление без приложения — страница `/delete-account` на лендинге (требование Google Play): вход почтой и паролем
→ подтверждение → `DELETE /me`.

### Синхронизация данных — документы коллекций

Как этап 1 в `docs/API.md`: `PUT /sync/{collection}`, `GET /sync/{collection}`, `GET /sync`. Дополнения:

- Список коллекций — файлы аккаунта из ядра: `sleep`, `nutrition`, `wellbeing`, `cognitive`, `calendar`,
  `fitness-state`, `screen-time`, `lineups`, `game-goals`, `faceit`, `player-survey`, `body-profile`.
  Неизвестную коллекцию сервер отклоняет. `sync-ledger.json` и глобальные файлы не отправляются.
- **Фото еды — отдельно.** Сейчас фото лежит base64 внутри `nutrition.json` (JPEG ~640 px). За месяц документ
  вырастет за лимит тела запроса Vercel (4,5 МБ). Поэтому: `PUT /photos/{meal_id}` (JPEG), `GET /photos/{meal_id}`;
  в синхронизируемом документе фото заменяется ссылкой/признаком, на телефоне фото остаётся как есть. Хранение —
  в Postgres (переносимость). Как именно вырезать и восстанавливать фото в документе — на усмотрение строителя.
- `PUT` принимает `If-Match`/`base_version` с версией, которую телефон видел последней. Политика конфликтов —
  **побеждает последняя запись документа** (бета, один основной телефон); версия нужна, чтобы телефон понял,
  что на сервере есть более новая копия, и сначала скачал её.
- Когда телефон синхронизируется:
  - **сразу после входа/подтверждения почты** — скачать все коллекции с сервера и разложить по папке аккаунта,
    потом загрузить сторы (это и есть «вошёл на новом телефоне — всё на месте»);
  - **после изменений** — отправка изменённых коллекций (`SyncLedger` уже отмечает) с небольшой задержкой
    (объединяем частые правки), при уходе приложения в фон и при появлении сети; фоновая отправка — WorkManager;
  - **при запуске** — `GET /sync`, и если на сервере коллекция новее локальной — скачать её.
- Офлайн приложение работает как сейчас; несинхронизированное уходит, когда появится сеть.
- **Конфликты — слияние по записям** (моё решение, из-за анти-цели «потерял данные»): если на сервере версия
  новее, телефон скачивает её и объединяет с локальной по `id` записей (локальные неотправленные записи
  сохраняются, при совпадении `id` побеждает локальная правка), затем отправляет результат. Удаления помечаются
  (список удалённых `id` в документе или в журнале синхронизации), чтобы удалённое не возвращалось. Документы
  без списков записей (цели, окно сна, профиль тела, анкета) — побеждает более новая правка целиком. Тот же
  механизм — при входе на телефоне, где у этого аккаунта уже есть данные.

### Команды и стафф — реальные данные

| Метод | Путь | Описание |
|---|---|---|
| GET | `/teams/me` | моя команда: название, код приглашения (только стафф), состав |
| GET | `/teams/{team_id}/players` | состав: ник, роль, последняя активность, ELO |
| GET | `/teams/{team_id}/players/{player_id}/sync/{collection}` | документ коллекции игрока **после фильтра прав** |
| GET | `/teams/{team_id}/players/{player_id}/photos/{meal_id}` | фото еды игрока |
| DELETE | `/teams/{team_id}/players/{player_id}` | стафф убирает игрока из команды |

- Права проверяются **на сервере**: стафф видит только игроков своей команды (`teamPlayer`); соло-игроки
  стаффу не видны.
- Фильтр по коллекциям: `lineups` — только записи с `visibility: team`; `player-survey` — анкета и **баллы**
  «Игрового характера», без ответов по пунктам; `body-profile` — **не отдаётся** (моё решение: возраст, рост
  и вес стаффу не показываем); остальные коллекции — как есть.
- Сводки, готовность, корреляции, лента еды команды **считаются на телефоне стаффа существующим кодом ядра**
  (`TeamAnalytics`, `TeamWeeklyBuilder`, `TeamFood`) поверх скачанных документов игроков (моё решение: расчёты
  уже есть и проверены тестами, переписывать их на сервер не нужно). Для этого `TeamAnalytics`/`GameData`,
  которые сейчас берут `DemoData.players`, должны принимать реальных игроков; демо продолжает работать на демо-данных.
- **Важно:** сейчас большая часть `TeamAnalytics` берёт ряды из генератора (`DemoData.playerSeries`) — готовность,
  баллы тестов, дни высокой усталости. Для реальных игроков метрики стаффа считаются из настоящих данных
  (моё решение):
  - готовность, фокус, усталость — из игровых тестов (`cognitive` → `game_results`: `readiness`, `focus`,
    `fatigue`), готовность дополняется настроением/энергией (`wellbeing`);
  - баллы когнитивных тестов — `cognitive` → `results`;
  - сон — `sleep`; нагрузка (ACWR) — `fitness-state`; экранное время — `screen-time`; еда — `nutrition`;
    ELO по дням — `faceit` (снимки);
  - игровые метрики (K/D, ADR, винрейт, «сон против K/D», корреляции с игрой) — телефон стаффа сам запрашивает
    матчи игрока у Faceit встроенным ключом по `player_id` из синхронизированного `faceit`;
  - метрика, для которой у игрока нет данных, показывается пустым состоянием («нет данных»), а не выдумывается;
    признак «требует внимания» считается только по тем метрикам, что есть.
  Формулы и пороги (например, «высокая усталость» = 8+ из 10) переносятся с демо как есть.
- **Состав команды** (моё решение): у команды один стафф-владелец; игрок состоит максимум в одной команде.
  Убранный из команды игрок становится соло и может вступить в другую команду по коду — в профиле появляется
  «Вступить в команду» (ввод кода). Второй стафф в команде — позже.
- Календарь команды (события стаффа, видимые игрокам) — **не в этой итерации** (моё решение; экраны календаря
  остаются личными).
- Регистрация стаффа в приложении открывается (`STAFF_NEEDS_SERVER` больше не показывается при включённом сервере).

### Аналитика использования

**Приём:** `POST /events` — пачка до 100 событий. Авторизация необязательна: события до входа (регистрация,
экран входа) идут с `install_id`, после входа — ещё и с `user_id` из токена.

Событие:

```json
{ "id": "uuid", "name": "screen_view", "ts": "2026-10-26T18:30:00Z",
  "install_id": "uuid", "session_id": "uuid", "screen": "sleep", "duration_ms": 41000,
  "props": { "tab": "state" },
  "app_version": "1.0.0 (7)", "os_version": "Android 16", "device": "Pixel 9", "locale": "ru-RU" }
```

- `id` — для защиты от дублей при повторной отправке.
- **Какие события** (стартовый набор; точные имена — на усмотрение строителя, но фиксируются в одном месте и
  в документации):
  - сессия: `session_start`, `session_end` (с длительностью); сессия заканчивается после 30 с в фоне;
  - экраны: `screen_view` при уходе с экрана, с `duration_ms` — для 5 вкладок и всех `Route`, листов и диалогов;
  - действия: записан сон / ночь вручную, добавлена еда (способ: фото/вручную), вода, тренировка, настроение,
    колесо баланса, пройден тест (вид), игровой тест, событие календаря, запись дневника CS2, подключён Faceit,
    открыты итоги недели, поделились итогами, изменены цели, подключён Health Connect, дан доступ к экранному
    времени, включены напоминания;
  - воронка: открыт экран регистрации, отправлена регистрация, подтверждена почта, вход, анкета: каждый шаг,
    «О тебе» сохранён, первая запись любого вида;
  - стафф: открыт игрок, аналитика команды, лента еды.
- **Без значений здоровья** — ни минут сна, ни ккал, ни пульса, ни веса, ни ответов. Только факт и категории
  (вид теста, способ ввода еды).
- **Свойства пользователя** (на сервере, не в каждом событии): роль, дата регистрации (когорта), команда/соло,
  тариф, источник установки (пока `beta`), версия приложения.
- На телефоне события копятся в файле очереди и уходят пачками: каждые ~30 с, при уходе в фон, при 50 событиях;
  без сети ждут. Очередь ограничена (старые выбрасываются при переполнении).
- **Демо-аккаунты и отладочные сборки события не шлют** (флаг сборки).
- Согласие на аналитику — часть условий бета-тестирования.

### Дашборд `/admin`

- Вход — обычный аккаунт Pulse, чей адрес в `ADMIN_EMAILS` (моё решение: без отдельного пароля админки).
  Без прав — 404.
- Фильтры: период, роль (соло / игрок команды / стафф), версия приложения.
- Метрики (как согласовано):
  - DAU / WAU / MAU и «липкость» DAU/MAU;
  - сессии на пользователя в день, средняя и медианная длительность сессии;
  - время по вкладкам и экранам: суммарное, на пользователя, доля пользователей, дошедших до экрана;
  - популярность действий (какие функции используют, сколько людей и как часто);
  - **полезность экранов**: удержание (вернулся через 1 / 7 дней) у тех, кто пользовался экраном, против тех,
    кто не пользовался;
  - воронка новичка: регистрация → почта подтверждена → анкета → «О тебе» → первая запись → вернулся на
    следующий день — с конверсией каждого шага;
  - удержание по когортам (неделя регистрации × неделя жизни), с разбивкой по роли;
  - частота ключевого действия («ценность»): ключевое действие = любая запись сна, настроения, еды, теста или
    тренировки; «получил ценность» = ключевое действие в 3+ разных днях за первые 7 дней (моё решение,
    порог — настройка);
  - список тестировщиков: регистрация, последняя активность, число сессий (без данных здоровья).
- Графики и таблицы — на усмотрение строителя; считается SQL-запросами по таблице событий.

### Лендинг (минимум)

`/` — что такое Pulse, как попасть в бету (контакт/ссылка), ссылки на документы. `/privacy`, `/terms`,
`/beta-terms`, `/delete-account`. Тёмная тема в стиле приложения; без маркетинговых блоков.

## Изменения в Android-приложении

- **Включение сервера по сборке:** `AppConfig.backend` берётся из `BuildConfig` (адрес API задаётся при сборке).
  Отладочная сборка может смотреть на локальный/preview-сервер; бета-сборка — на бета-сервер.
- **Регистрация:** галочка «Принимаю условия бета-тестирования» (обязательная, со ссылкой на текст), после отправки —
  **экран ввода кода из письма** (повторная отправка с таймером), затем вход.
- **Вход:** обработка `email_not_verified` → экран кода. **«Забыли пароль?»** → почта → код → новый пароль.
- **Выход** вызывает `/auth/logout`; **удаление аккаунта** — `DELETE /me` и стирание локальной папки (уже есть).
- **Синхронизация:** вызовы `SyncEngine` по правилам выше; скачивание всех коллекций при входе; фото еды —
  отдельной загрузкой.
- **Стафф:** регистрация стаффа открыта; экраны стаффа («Игроки», карточка игрока, «Аналитика команды»,
  корреляции, лента еды, итоги недели команды) показывают реальных игроков команды; код приглашения виден в
  профиле стаффа и им можно поделиться. Пустые состояния: «В команде пока нет игроков — поделитесь кодом».
- **Аналитика:** трекер в ядре (очередь + отправка), подключённый к навигации (`AppTab`, `Route`, листы) и к
  действиям в сторах/экранах.
- Демо (`«Посмотреть демо»`) работает как сейчас, полностью локально.
- Тексты документов в приложении (`LegalTexts.kt`) и `docs/privacy-policy.md`, `docs/terms.md` обновляются:
  данные хранятся на сервере, собирается аналитика использования; новый документ — условия бета-тестирования.

## Ручные шаги владельца

1. Подключить Neon Postgres к проекту в Vercel (маркетплейс → принять условия).
2. Купить домен (можно в Vercel) и привязать к проекту.
3. Завести Resend, добавить домен, внести DNS-записи (строитель подскажет какие).
4. (Желательно) завести Sentry.
5. Указать свой адрес в `ADMIN_EMAILS`.

Строитель не покупает, не принимает условия и не вводит платёжные данные за владельца.

## Тестирование

- Сервер: тесты на каждый эндпоинт (успех, ошибки, права стаффа, фильтры коллекций, лимиты, ротация токенов,
  удаление аккаунта) против настоящего Postgres (локальный или отдельная ветка Neon), не моков базы.
- Ядро и Android: тесты клиента против фейкового HTTP (Ktor MockEngine) — регистрация с кодом, синхронизация,
  восстановление на «новом телефоне», очередь аналитики, фильтр демо.
- Сквозная проверка на эмуляторе против preview-деплоя: регистрация → письмо → код → данные → переустановка →
  данные вернулись; стафф видит игрока; события видны в `/admin`.

## Этапы (порядок — моё решение)

1. Сервер: каркас, база и миграции, регистрация/вход/почта/сброс, профиль, удаление; деплой на Vercel.
2. Синхронизация документов и фото; Android: включение сервера, экраны почты, синхронизация.
3. Аналитика: приём событий, трекер в приложении, дашборд `/admin`.
4. Команды и стафф на реальных данных (сервер + экраны стаффа).
5. Лендинг и документы, бета-сборка, сквозная проверка.

## Ответы владельца после проверки

- **Старые локальные аккаунты:** у тестировщиков нет данных, которые жалко потерять — **начинаем с нуля**.
  Бета-сборка входит только через сервер; локальные аккаунты скрываются, их данные на сервер не переносятся.
  Демо остаётся локальным.
- **Раздача беты — APK напрямую**, как сейчас. Закрытый тест Google Play, AAB, анкета Data Safety и декларации
  разрешений — не в этой итерации. Страница `/delete-account` всё равно делается (пригодится для Play).
- **Масштаб: до 30 тестировщиков на 1–2 месяца.** Хватает бесплатных Neon (0,5 ГБ) и Resend (100 писем в день).
  Сырые события хранятся 90 дней; фото еды — в размере, в котором их уже сжимает приложение (~640 px, JPEG 70).
  Строитель добавляет в `/admin` простую строку «занято места в базе» — чтобы вовремя увидеть упор в лимит.
